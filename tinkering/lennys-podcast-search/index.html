Lenny's Podcast Search

Try it now →

TL;DR

  • Built a semantic search engine for 300+ Lenny's Podcast episodes (~2,000+ hours of content).
  • Hybrid retrieval: combines dense vectors (OpenAI embeddings) with sparse vectors (BM25) using RRF fusion.
  • Cross-encoder reranking with BGE-reranker-large for final precision.
  • Speaker-turn aware chunking preserves Q&A context from host-guest conversations.
  • Contextual chunk enrichment using Claude Haiku improves embedding quality.
  • Deep links jump directly to the exact YouTube timestamp for each result.

The Problem

Lenny's Podcast is a goldmine of product management, growth, and leadership wisdom. 300+ episodes featuring guests from Airbnb, Stripe, Notion, Figma, and more. But finding specific insights is painful:

  • YouTube search is keyword-based—misses semantic meaning
  • No way to search across all episodes at once
  • Even if you find an episode, scrubbing to the right moment is tedious

I wanted to ask questions like "how did Airbnb approach growth in the early days?" and get direct answers with timestamps.

Deep Dive: Speaker-Turn Aware Chunking

Most RAG systems use naive sliding window chunking. For podcasts, this destroys context—you get half a question in one chunk and half an answer in another.

My chunker understands the conversation structure:

1 Parse Speaker Turns

Each transcript is parsed into speaker turns with timestamps. Speaker diarization identifies who's talking (Lenny vs guest).

SpeakerTurn(speaker, role, content, timestamp_seconds, is_sponsor)

2 Detect Q&A Pairs

When a host turn is immediately followed by a guest turn, and combined tokens < 400, they're grouped as a single chunk. This preserves question-answer context.

chunk_type="qa_pair" | "host_question" | "guest_answer"

3 Merge Short Turns

Consecutive short turns from the same speaker are merged if combined < 512 tokens. Prevents tiny fragments.

cl100k_base tokenizer (same as GPT-4)

4 Split Long Monologues

Turns exceeding 512 tokens are split at sentence boundaries with 50-token overlap to maintain continuity.

split_long_text_with_overlap(text, max_tokens=512, overlap_tokens=50)

Topic Extraction

Each chunk is tagged with topics using regex patterns:

TOPIC_PATTERNS = {

This enables filtered search: "show me what Brian Chesky said about hiring" filters by guest="Brian Chesky" AND topic="hiring".

Deep Dive: Contextual Chunk Enrichment

A chunk like "I think that's really important" is meaningless without context. Anthropic's Contextual Retrieval paper showed that prepending context improves retrieval by 49%.

For each chunk, Claude Haiku generates 2-3 sentences of context:

CONTEXT_PROMPT = """<episode>
Title: {episode_title}
Guest: {episode_guest}
</episode>

<previous_context>
{previous_context}  // Last 2 chunks
</previous_context>

<current_chunk>
{speaker} ({timestamp}): {chunk_content}
</current_chunk>

Generate a brief context (2-3 sentences) that situates this chunk:
1. What topic/question is being discussed
2. Any specific companies, frameworks, or concepts referenced
3. The speaker's role and expertise if relevant"""

The context is prepended to each chunk before embedding. So "I think that's really important" becomes:

Contextualized Chunk Example

"Brian Chesky, CEO of Airbnb, is discussing the importance of hands-on customer research in the early stages. He's responding to Lenny's question about how Airbnb validated product-market fit. I think that's really important..."

Deep Dive: Hybrid Retrieval with RRF

Dense (semantic) search is great for meaning, but misses exact keyword matches. Sparse (BM25) search catches keywords but misses synonyms. Hybrid combines both.

The Retrieval Pipeline

def search(self, query, filters):
    # 1. Dense search (semantic similarity)
    query_embedding = embedder.embed_query(query)
    dense_results = vector_store.search(
        query_embedding=query_embedding,
        top_k=15,
        guest_filter=filters.guest,
        speaker_role_filter=filters.speaker_role,
        topic_filter=filters.topic,
        exclude_sponsors=True
    )

    # 2. Sparse search (keyword matching)
    bm25_results = bm25_retriever.search(query, top_k=15)

    # 3. RRF fusion
    fused = reciprocal_rank_fusion(
        [dense_results, bm25_results],
        k=60
    )

    return fused[:20]

Reciprocal Rank Fusion (RRF)

RRF combines ranked lists without needing score normalization:

# For each document d in the combined results:
score(d) = Σ 1/(k + rank(d))

# k=60 is the standard constant
# If doc is rank 1 in dense and rank 3 in BM25:
# score = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323

Documents that appear in both lists get boosted. Documents that only appear in one list still contribute.

Deep Dive: Cross-Encoder Reranking

Bi-encoders (like OpenAI embeddings) encode query and document separately. Fast, but limited. Cross-encoders process query AND document together through the transformer—much more accurate but slower.

class BGEReranker:
    def __init__(self, model_name="BAAI/bge-reranker-large"):
        self.device = "mps" if torch.backends.mps.is_available() else "cpu"
        self._reranker = None  # Lazy loaded

    def rerank(self, query, results, top_n=5):
        # Lazy load model on first use
        if self._reranker is None:
            from FlagEmbedding import FlagReranker
            self._reranker = FlagReranker(self.model_name, use_fp16=True)

        # Create query-document pairs
        pairs = [[query, r["text"]] for r in results]

        # Score all pairs at once
        scores = self._reranker.compute_score(pairs, normalize=True)

        # Sort by rerank score
        for r, score in zip(results, scores):
            r["rerank_score"] = float(score)

        return sorted(results, key=lambda x: x["rerank_score"], reverse=True)[:top_n]

The reranker takes the top 20 RRF results and re-scores them, returning the top 15. This final pass dramatically improves precision.

Deep Dive: BM25 Lightweight Mode

Full BM25 index with chunk metadata uses ~150MB RAM. For deployment on memory-constrained servers, I implemented lightweight mode:

class BM25Retriever:
    def __init__(self, lightweight_mode=False):
        self.lightweight_mode = lightweight_mode
        # In lightweight mode, only store chunk_ids (~5MB vs ~150MB)
        self.chunk_ids: list[str] = []

    def search(self, query, top_k=15):
        if self.lightweight_mode:
            # Return only chunk_ids, no metadata
            # HybridRetriever fetches full data from Qdrant
            return [{ "chunk_id": self.chunk_ids[idx] } for idx in results]

The hybrid retriever enriches BM25 results from Qdrant, applying filters there instead. Saves 100MB+ with minimal latency impact.

Key Takeaway

Hybrid retrieval is the secret sauce. Dense search alone misses exact matches. BM25 alone misses semantic similarity. RRF fusion + cross-encoder reranking gives you the best of both worlds.

And for conversational content like podcasts, speaker-turn aware chunking is essential. Don't break up Q&A pairs.
